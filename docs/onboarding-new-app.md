# Onboarding a new app

The recipe for adding one app to the suite: from a CLI on the PATH to a
declared upstream with its content tier, green tests and the spec rows
updated. The three most recent additions (anicraft, craft-anything,
mailcraft) followed it step for step.

The suite is the launcher's nineteen apps; every one of them exposes an
`mcp` subcommand that answers the stdio handshake, and each is declared in
the connector (CONN-CRAFT-SUITE-API-APPS-R002).

## 1 — Verify the CLI live

Install the app's deb on a host with the app's CPU features (AVX2; the
rendering apps need `LIBGL_ALWAYS_SOFTWARE=1` on headless boxes) and prove
the MCP surface by hand:

```bash
anicraft mcp            # stdio: the tools/list handshake
```

Note the tool names, their count and the server version. The app's own MCP
tool names are what the facade will serve, namespaced.

## 2 — Declare the upstream

In `craft_suite_api/upstreams.py`:

- add the app name to `APPS`;
- if the name cannot be an SDK namespace (the grammar is
  `^[a-z][a-z0-9]{1,23}$` — a hyphen breaks it), map it in `NAMESPACES`:
  `craft-anything` is declared with `namespace="craftanything"`, and its
  tools are served as `craftanything_*`;
- if the app's `mcp` subcommand rejects the automation-root flags, add it
  to `FLAGLESS_APPS` (it runs rootless, like the other flagless apps).

The declaration fails closed at import time: a bad namespace or an unsafe
root raises before the server starts.

## 3 — Declare the dispatch

In `craft_suite_api/app_commands.py`, one `Dispatch` entry per app:
`Dispatch(list_tool, run_tool, id_arg=...)` names the app's registry
listing command and its runner. Two shapes:

- **generated command tools** (the default): every engine command of the
  listing becomes a `<app>_cmd_<command>` tool, warmed at server start;
- **no dispatch** (`run_tool=None`, `generate=False`): the app's own typed
  MCP tools are served as-is, nothing is generated or hidden
  (craft-anything, and lightcraft's per-command surface).

## 4 — Confirm discovery is closed

`craft_suite_api/probe.py` holds `REPROBED`: candidate names the suite has
not declared yet. With the app declared it stays `()` — discovery for new
apps is manual (the launcher's README is the source of truth).

## 5 — Author the content source

`content/apps/<app>.yml` (see an existing app for the shape):

```yaml
app: mailcraft            # the app name; a namespace key only when it differs
summary: one line
classes:                  # each parent from the allowed set
  - name: Mailbox
    parent: Document      # CreativeWork | Document | Artifact | App | AppTool
    description: ...
functionality:            # each names only snapshot tools
  - name: read_messages
    description: ...
    tools: [list_folders, list_messages, read_message]
    steps: [...]
```

Every tool named anywhere must exist in the app's snapshot; the generators
refuse the rest.

## 6 — Capture the snapshot

On a host with the CLI installed, in the project venv:

```bash
uv run python scripts/generate_app_content.py --refresh
```

writes `content/snapshots/<app>.tools.json` for every app (a single app via
`refresh_app`). The snapshot is the live `tools/list` plus the server
version.

## 7 — Generate, then gate

```bash
uv run python scripts/generate_app_content.py --write    # renders the app's files
uv run python scripts/generate_app_content.py --check    # the offline drift gate
```

`--write` renders `craft_suite_api/ontology/artcraft-<app>.ttl`,
`craft_suite_api/skills/<app>/SKILL.md` and one
`craft_suite_api/prompts/<app>-<functionality>.json` per functionality, all
namespaced with the app's served namespace. `--check` must read
`check clean: N apps`; the phase 3 gate runs it on the committed content.

## 8 — Update the counts

A suite change moves every count-sensitive surface:

- `tests/test_upstream_declarations.py` — declaration count, `FLAGLESS_APPS`,
  `NAMESPACES`, per-app roots;
- the phase gates — fixture upstreams pass
  `namespace=NAMESPACES.get(app)`, tool counts scale with the suite;
- the content render tests iterate the live `APPS` and the served
  namespace;
- `docs/tool-budget.md` — the per-app table and the totals;
- the specs — the `specs/` rows that name the suite size. `status.json`
  files are regenerated by the pipelines hook, never hand-edited.

## 9 — Ship the follow-on lanes and prove it

The connector PR lands first; then:

1. **image**: add the app's deb URL and its release sha256 to
   `images/craft-suite-api-artcraft/artcraft-debs.sha256` and bump the tag;
2. **service**: pin the new image; if the suite outgrows the SDK defaults
   (active-namespace cap 4, process pool 16), raise
   `SCION_UPSTREAMS_MAX_ACTIVE_NAMESPACES` and
   `SCION_UPSTREAMS_MAX_PROCESSES` in the manifests (see
   [fleet deployment](fleet-deployment.md));
3. **proven workflows**: once the image serves, prove a real workflow
   through the app on the deployment host and record it as the app's
   R009 content (skill, agent prompt, ontology) — or record the attempt as
   a follow-up.

## Gotchas

- **Namespace grammar**: the SDK's first underscore splits the namespace
  from the tool name, and hyphens are not allowed — a hyphenated app must
  get a `NAMESPACES` entry, and every test and generated file follows the
  served namespace, not the app name.
- **Root flags are per app**: probe with real flags, not `--help` (some
  parsers break on it); an app that rejects the root flags is flagless.
- **Early-alpha apps** may need a coding agent on the host for their build
  workflows even though their study/inspect surface works standalone —
  say so in the app's skill.
- **The pool caps are real**: beyond `SCION_UPSTREAMS_MAX_PROCESSES` a late
  namespace activates but cannot spawn until an older child goes idle.
