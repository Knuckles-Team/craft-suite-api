Shape: add `BackendNotConfigured` to `craft_suite_api/error_authority.py`, raise it from `get_client`, and map it to the refusal in `OpenApiTool.run`. Reuse the SDK problem mapping. Refusal code: `BACKEND_NOT_CONFIGURED`. Knobs: none. Depends on: `CONN-CRAFT-SUITE-API-R003`, `SCION-CONNECTOR-CONTROL-R065`. | `tests/test_tier1_degrade.py::test_unconfigured_backend_lists_tools_and_refuses_typed` (planned in `test-spec.md`). | `CONN-CRAFT-SUITE-API-APPS-R002` | **Declare the eleven app upstreams.** Subsystem: upstream registry declarations. Add `craft_suite_api/upstreams.py` with the tuple `UPSTREAMS` of eleven `UpstreamDecl` values (`SCION-CONNECTOR-CONTROL-R914.1`), one for each of photocraft, wordcraft, pdfcraft, solidcraft, vectorcraft, figcraft, effectcraft, filmcraft, soundcraft, deckcraft and cadcraft. Each has `name` and `namespace` equal to the app name, `kind` `stdio`, `command` `<app>-cli`, `args` `("mcp",)` and an unset `activation`. Each `sandbox` has `read_flag` `--automation-read-root` and `write_flag` `--automation-write-root`, except for `filmcraft` and `cadcraft`: their `mcp` subcommand has no root flags (`filmcraft-cli mcp` refuses them as an unknown option), so both declare `read_flag` and `write_flag` as `None` and empty roots, and the loader passes no root flag to them (`SCION-CONNECTOR-CONTROL-R914.2`). Consequence: the two root settings never reach those two apps, so their file access is bounded by the container filesystem, not by a flag, and calls with a `path` argument still run through the artifact exchange (`CONN-CRAFT-SUITE-API-APPS-R013`). The read roots come from the setting `CRAFT_SUITE_READ_ROOTS` and the write roots from `CRAFT_SUITE_WRITE_ROOTS`. Each setting holds absolute paths split by the platform path separator. An unset setting yields an empty tuple, which denies access (`SCION-CONNECTOR-CONTROL-R914.2`). The write roots never default to the read roots. Refusal: a relative path in either setting refuses with `UPSTREAM_ROOT_UNSAFE` from the SDK. Knobs: the two settings; starting value unset. lightcraft, designcraft and gridcraft are not declared until `CONN-CRAFT-SUITE-API-APPS-R003` reports that they expose `mcp`. Caller chain: `run` → `build_server` → `_serve_hooks` (in the `scion-sdk` package, module `scion_sdk._connector_serve`, line 97) → `attach_upstreams`, which reads `connector.upstreams`; the `Connector` in `craft_suite_api/__init__.py:34` passes `upstreams=UPSTREAMS`. Shape: `craft_suite_api/upstreams.py` builds the tuple with a loop over an app tuple; the `Connector(...)` call gains one argument. Depends on: `SCION-CONNECTOR-CONTROL-R914.1`, `SCION-CONNECTOR-CONTROL-R914.2`, `SCION-CONNECTOR-CONTROL-R914.5`. | `tests/test_upstream_declarations.py::test_eleven_apps_declared_with_roots_fail_closed` (planned in `test-spec.md`). Eleven declarations exist with unique namespaces. With both settings unset, each command line holds no root flag. With one read root set, each holds one read flag pair and no write flag, except `filmcraft` and `cadcraft`, whose command line is `<app>-cli mcp` with no root flag whatever the settings. |
| `CONN-CRAFT-SUITE-API-APPS-R003` | **Probe the app command-line tools for MCP support.** Subsystem: app discovery. Add the console script `craft-suite-probe` (`scripts/probe_app_clis.py`). The operator or a host job runs it after each app update. This is how lightcraft, designcraft and gridcraft are re-probed. Knob: `probe_timeout_s` 20 (range 5..120). Caller chain: operator runs `craft-suite-probe` → `main` in `scripts/probe_app_clis.py` → the SDK MCP client over stdio. Shape: one module that loops over `APPS` from `craft_suite_api/upstreams.py` plus the three re-probed names; it reuses the SDK client and writes no file. Depends on: `CONN-CRAFT-SUITE-API-APPS-R002`. | `tests/test_probe_apps.py::test_probe_reports_declared_undeclared_and_missing` (planned in `test-spec.md`). | `CONN-CRAFT-SUITE-API-APPS-R013` | **Bind each app to the artifact exchange.** Subsystem: upstream registry declarations. Each `UpstreamDecl` in `craft_suite_api/upstreams.py` sets `exchange=ExchangeBinding(path_args=("path", "dir", "out", "out_dir"))` (`SCION-CONNECTOR-CONTROL-R914.13`). With exchange settings present, each app then receives the exchange input tree as a read root and the output tree as a write root. Each app call runs in its own run directory. A relative output path lands in that directory, and the SDK publishes the files after the call. Without exchange settings, the binding is inert and the apps behave as before. Refusal codes: the SDK exchange codes pass through unchanged. Knobs: none in this connector. Caller chain: `run` → `build_server` → `_serve_hooks` (in the `scion-sdk` package, module `scion_sdk._connector_serve`, line 97) → `attach_upstreams`, which reads each declaration's `exchange` field. Shape: one keyword added in `build_upstreams`; no connector mechanism. Depends on: `CONN-CRAFT-SUITE-API-APPS-R002`, `SCION-CONNECTOR-CONTROL-R914.13`. | `tests/test_artifact_exchange.py::test_every_app_declares_the_exchange_binding` (planned in `test-spec.md`). All eleven declarations carry the binding with the four path arguments. |
