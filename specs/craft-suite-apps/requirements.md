| `CONN-CRAFT-SUITE-API-APPS-R017` | **Every app engine command is its own tool.** Subsystem: app tool surface. Each app keeps an engine command registry of hundreds of commands that its own `mcp` reaches only through one dispatch tool (for example `photocraft_command_run` with `id`). The connector serves each registry command as one tool named `<app>_cmd_<command id>` (non-name characters become `_`; names stay within 64 characters with a stable hash suffix and stay unique). The description carries the app's own label, parameter documentation and menu (cut at 1000 characters; `<app>_list_commands` keeps the full text); the input schema names each documented top-level parameter once, without repeating its documentation (the app's JSON schema when it publishes one, as effectcraft does), plus the dispatch tool's context arguments such as `doc`, `document` or `wait` (type and a 120-character description), and admits further properties. Each tool carries the SDK `scion/upstream` metadata of its app and a read-only hint only where the app marks the command as not mutating, so the whole listing (about 9,000 tools) stays near 6 MB, inside the 8 MiB single-response limit of the fleet gateway. A call forwards to the app's dispatch tool on the same server with the command id and the remaining arguments as `params`, so the activation gate, pool, artifact exchange and audit apply unchanged. The single-command dispatch tools are dropped from listings (`HideDispatchTools`) but stay callable by name for the forwarding; lightcraft already serves one tool per command, so only its dispatch tools are hidden. Each tool carries the tag `ns:<app>`, so lazy activation hides and shows it with its app. The registries are read at serve time over a short-lived `<app>-cli mcp` child per app, concurrently at server start, so the tools always match the installed apps and nothing is generated into the repository. Refusal: an app whose registry cannot be listed or parsed serves no command tool and logs `APP_REGISTRY_UNREADABLE` with the app name; the server and the other apps are unaffected. Knobs: the SDK `SCION_UPSTREAMS_DISABLED` list also drops an app's command tools; the registrar toggle `APP_COMMANDTOOL` (start true) turns the surface off. Caller chain: `_serve_hooks` → `register_tool_surface` → `register_app_command_tools` (`craft_suite_api/mcp/__init__.py`) → `AppCommandProvider` (`craft_suite_api/app_commands.py`); MCP `tools/call` of `<app>_cmd_<id>` → `CommandTool.run` → `FastMCP.call_tool` of `<app>_<dispatch tool>`. | `CONN-CRAFT-SUITE-API-APPS-R018` | **Each app warms on its own; startup never blocks.** Subsystem: app tool surface, readiness. Entry point: the connector server's lifespan and `/ready`. Caller chain: `register_app_command_tools` (`craft_suite_api/mcp/__init__.py`) adds `SessionTracker` and `AppCommandProvider` (`craft_suite_api/app_commands.py`); the provider's lifespan starts one load task per app (`_load_one`), each listing that app's registry over a short-lived `<app>-cli mcp` child. Shape: the server answers `/health` and `tools/list` as soon as it serves; a listing returns the command tools of every app loaded so far and never waits for a warming app. When an app's registry lands, its tools join the listing and `ToolsListChanged` is published on the SDK change bus (`subscriptions/listen` streams) and sent as `notifications/tools/list_changed` to every handshake-era session seen. A call to a command of an app still warming waits up to `CRAFT_SUITE_WARMUP_WAIT_S` (default 20 s) for that app alone; if it is still warming the call answers the typed, retryable refusal `APP_WARMING` (`is_error`, structured `{refused, code, app, tool, retryable: true, retry_after_s}`).
